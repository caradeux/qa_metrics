03

Ruta de la petición

Cómo viaja una solicitud del analista, desde el navegador hasta la base de datos y las integraciones externas.

1

Resolución y TLS

Route 53 resuelve el dominio al ALB; ACM termina el certificado TLS. El tráfico entra por el puerto 443.

2

Balanceo por host

El ALB enruta qa-metrics… al servicio Web y api.qa-metrics… al servicio API, ambos en Fargate.

3

Renderizado y lógica

Web (Next.js) hace SSR y llama a la API (Express); ambos leen/escriben en Postgres vía Prisma (pg).

4

Persistencia

Consultas a RDS PostgreSQL en subred privada por el puerto 5432. Sin exposición pública.

5

Generación de reportes

La API produce PPTX / Excel / PDF con gráficos server-side (picos de CPU puntuales) y los entrega o los guarda en S3.

6

Integraciones salientes

Correo vía Resend y carga de horas a FlowPilot salen a internet por el NAT Gateway.

Justificación por componente

Por qué cada servicio entra en la arquitectura, por qué se eligió frente a sus alternativas, y cómo se ancla en el código real de la aplicación (monorepo turbo: apps/web, apps/api, packages/database).

ECS
ECS Fargate — Web
Cómputo · Frontend Next.js 16
Por qué se necesita
El front es Next.js 16 con SSR y next-auth: no es un sitio estático, necesita un runtime Node siempre disponible que ejecute el contenedor de apps/web/Dockerfile y renderice páginas por request.
Por qué este servicio
Fargate corre la misma imagen Docker que hoy usan en Coolify, sin administrar servidores ni parches del SO. Paridad 1:1 con el despliegue actual.
Alternativas descartadas
EC2: obliga a gestionar SO/escalado. Lambda: SSR de Next requiere adaptadores y sufre cold-starts para una app interna. S3+CloudFront: no sirve, el contenido es dinámico.
Dimensionamiento
SSR es liviano en CPU a esta carga: 0.5 vCPU / 1 GB, 2 tareas tras el ALB para HA.
ECS
ECS Fargate — API
Cómputo · Backend Express 5
Por qué se necesita
La API (apps/api) hace auth JWT/bcrypt y —lo determinante— genera reportes pesados: PPTX (pptxgenjs), Excel (exceljs), PDF (jspdf) y gráficos server-side con chartjs-node-canvas (render en canvas nativo, intensivo en CPU/memoria).
Por qué este servicio
Servicio Fargate separado del web para que un reporte pesado no degrade la navegación, y para escalar/dimensionar cada uno por su cuenta. bcrypt y canvas son CPU-bound; Fargate permite subir el tamaño de la tarea sin cambiar de plataforma.
Alternativas descartadas
Monolito web+api en un contenedor: acopla el escalado. Lambda: los reportes con canvas y libs nativas exceden límites cómodos de tamaño/tiempo.
Dimensionamiento
1 vCPU / 2 GB base; los picos de reporte son puntuales, no sostenidos → 2 tareas absorben concurrencia sin sobredimensionar.
RDS
RDS for PostgreSQL 16
Base de datos
Por qué se necesita
El dominio es 100% relacional: 24 modelos Prisma con FKs (Users, Testers, Projects, TestCycles, UserStory, DailyRecord, Flowpilot*, Automation*…). El motor actual ya es Postgres 16.
Por qué este servicio
RDS gestionado da backups automáticos, parcheo, snapshots y Multi-AZ sin operar la base. Sobre esta instancia corre prisma migrate deploy, igual que hoy.
Alternativas descartadas
Postgres en contenedor/EC2: obligaría a gestionar almacenamiento persistente y respaldos a mano. Aurora: más caro y de mayor escala que la necesaria (<5 GB, baja concurrencia).
Dimensionamiento
db.t4g.small (Graviton, costo-eficiente) + 20 GB gp3; Multi-AZ solo en el escenario de Alta disponibilidad.
ALB
Application Load Balancer
Red · Ingreso L7
Por qué se necesita
Dos servicios (web + api) tras un único punto de entrada HTTPS con enrutado por host: qa-metrics… → web y api.qa-metrics… → api (exactamente los dominios en uso). Terminación TLS y health checks.
Por qué este servicio
Es capa 7: entiende host/path HTTP, que es justo el enrutado requerido, e integra con ACM para TLS y con los target groups de ECS.
Alternativas descartadas
NLB: es L4, no rutea por host. API Gateway: pensado para APIs, no para servir el SSR. CloudFront: no aporta a una app interna dinámica sin contenido cacheable.
Dimensionamiento
1 ALB · 2 target groups (web/api).
NAT
NAT Gateway
Red · Egress
Por qué se necesita
Las tareas Fargate están en subredes privadas sin IP pública, pero deben salir a internet para enviar correo por Resend y sincronizar horas con FlowPilot (flowpilot.biz). Sin NAT no hay egress.
Por qué este servicio
NAT gestionado por AWS: alta disponibilidad y sin administrar una instancia NAT propia.
Alternativas descartadas
En el escenario mínimo se sustituye por VPC Endpoints (S3/ECR) + tareas con IP pública restringida por Security Group, evitando su costo fijo.
Dimensionamiento
1× (2× en Alta disponibilidad, uno por AZ). Es el típico costo fijo "sorpresa" → por eso se muestra el modo sin él.
S3
Amazon S3
Almacenamiento de objetos
Por qué se necesita
Hoy los uploads (multer) se parsean en memoria y los reportes se generan al vuelo. Para retener evidencias y reportes (auditoría, re-descarga) hace falta almacenamiento duradero fuera del disco efímero de la tarea.
Por qué este servicio
Durabilidad de 11 nueves, muy barato, y presigned URLs para descargas directas sin pasar por la API.
Alternativas descartadas
Guardar binarios en Postgres: infla la DB y los backups. EFS: innecesario y más caro para objetos.
Dimensionamiento
~10 GB Standard; lifecycle a Infrequent Access para reportes antiguos.
ECR
Elastic Container Registry
Cómputo · Registro
Por qué se necesita
Fargate necesita un registro desde donde traer las imágenes; hoy se construyen dos imágenes (apps/web/Dockerfile, apps/api/Dockerfile).
Por qué este servicio
Registro privado integrado con IAM: Fargate hace el pull sin credenciales externas.
Alternativas descartadas
Docker Hub: registro público, rate limits en el pull y credenciales que gestionar.
Dimensionamiento
~2 GB de imágenes con scan de vulnerabilidades activado.
SM
Secrets Manager
Seguridad · Secretos
Por qué se necesita
La app maneja secretos reales: JWT_SECRET, JWT_REFRESH_SECRET, ENCRYPTION_KEY (que cifra las credenciales de FlowPilot del usuario) y DATABASE_URL. Hoy viajan como variables de entorno.
Por qué este servicio
Cifrado en reposo, rotación y auditoría de acceso; los secretos no quedan expuestos en la definición de tarea. La tarea los lee vía rol IAM.
Alternativas descartadas
Env vars en la task definition: quedan legibles en la consola. SSM Parameter Store (SecureString) es opción más barata si no se requiere rotación automática.
Dimensionamiento
~4 secretos. (El descubrimiento de FlowPilot dejó un password de ambiente QA a rotar.)
CW
CloudWatch
Gestión · Observabilidad
Por qué se necesita
La API loguea con pino; se necesita centralizar logs de los contenedores, métricas (CPU/mem de Fargate, conexiones RDS, 5xx del ALB) y alarmas (p. ej. fallo de sync a FlowPilot, CPU alta durante reportes).
Por qué este servicio
Nativo con ECS/RDS/ALB: recoge logs y métricas sin instalar agentes.
Alternativas descartadas
Datadog/Grafana Cloud: válido solo si ya existe observabilidad corporativa estandarizada (costo adicional).
Dimensionamiento
Log groups + ~5 alarmas + dashboard básico.
R53
Route 53 + ACM
Red · DNS y TLS
Por qué se necesita
Los dominios ya en uso —qa-metrics.inovabiz.com y api.qa-metrics.inovabiz.com— deben resolver al ALB, con TLS válido (las cookies Secure exigen HTTPS).
Por qué este servicio
ACM emite y renueva certificados gratis y automáticamente para el ALB; Route 53 aporta alias records al ALB con health checks.
Alternativas descartadas
Si el DNS de inovabiz.com vive en otro proveedor, se delega solo el subdominio o se usan CNAME; ACM sigue siendo el emisor del certificado.
Dimensionamiento
1 hosted zone + certificados gestionados.
VPC
Virtual Private Cloud
Red · Aislamiento
Por qué se necesita
Aislar la aplicación: subredes públicas (ALB, NAT) y privadas (Fargate, RDS), de modo que la base nunca sea accesible desde internet. Security Groups que solo permitan el camino ALB → Fargate → RDS.
Por qué este servicio
Postura de seguridad por defecto; los VPC Endpoints (S3/ECR) evitan que ese tráfico pase por el NAT (menos costo y superficie).
Alternativas descartadas
Todo en subred pública: expondría la DB y el cómputo; inaceptable incluso para uso interno.
Dimensionamiento
2 AZ · subred pública + privada por AZ · SG por capa.

08

Supuestos y exclusiones

Base sobre la que se construyen las cifras. Cualquier cambio impacta el costo.

  • Región base us-east-1. Se muestra sa-east-1 como referencia para Chile; elegir región es decisión de arquitectura por latencia/compliance.
  • Precios On-Demand, sin compromisos. No incluyen Savings Plans, Reserved ni descuentos de contrato AWS.
  • No incluye impuestos (IVA), soporte AWS (Business ~$100/mes o 10 %), ni costos de migración inicial.
  • Resend y FlowPilot son SaaS externos: su costo es aparte (Resend ~$0–20/mes según volumen). Opción: migrar correo a Amazon SES (~$0.10/1000 correos).
  • Sin colas, cron ni workers en el código actual: los reportes se generan síncronos on-demand. No se presupuestan SQS/Lambda.
  • Almacenamiento persistente hoy es mínimo: los uploads se parsean en memoria. S3 se incorpora como buena práctica para retener evidencias/reportes.
  • HA de datos opcional: el escenario Recomendado usa RDS Single-AZ con backups; Multi-AZ se reserva para el escenario de Alta disponibilidad.
  • Tráfico modesto: herramienta interna sin exposición pública masiva; no se presupuesta WAF/Shield Advanced.

Con el MCP activo, cada línea de la tabla del punto 06 se reemplaza por el valor exacto que devuelve la AWS Price List API, incluyendo variaciones por región y tipo de instancia.
