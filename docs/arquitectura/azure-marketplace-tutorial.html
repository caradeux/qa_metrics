00 Base común

Prerequisitos para cualquier ruta

Antes de tocar el offer, la cuenta de publicación y el entorno de trabajo tienen que estar listos. Esto se hace una sola vez.

0.1
Cuenta de Partner Center + Commercial Marketplace

Todo el Marketplace se administra desde Partner Center. Necesitas una cuenta con el programa Commercial marketplace habilitado.

  • Entra a Partner Center y crea/accede a la cuenta de Inovabiz (probablemente ya existe si son partner Microsoft).
  • Menú Settings → Account settings → Programs → inscribir Commercial marketplace.
  • Completa la verificación de identidad de negocio (razón social, dominio, dirección) — tarda de horas a días.
  • Configura el perfil de pago y fiscal (solo obligatorio si vas a cobrar — Ruta B, o Ruta A de pago).

◆ Tip

Anota tu Microsoft/Partner ID (MPN). Lo pedirán en varias pantallas y en la asociación de la cuenta de facturación.

0.2
Entorno de trabajo local

Herramientas para construir, empaquetar y validar los artefactos que subirás.

bash · setup
# Azure CLI + extensión de Bicep
az upgrade
az bicep install
az login
az account set --subscription "<tu-subscripcion-de-pruebas>"

# Verifica versiones
az version
az bicep version   # >= 0.30
  • Una subscripción Azure de pruebas para desplegar y validar antes de publicar.
  • Docker (ya lo usas) para construir apps/api y apps/web.
  • Acceso de escritura al repo para versionar los artefactos del offer.

Ruta A Azure Application · Solution Template

El cliente instala tu app en su subscripción

Empaquetas tu infraestructura como una plantilla que el cliente despliega con un formulario guiado. Es el camino más rápido porque ya tienes el Bicep que crea Postgres + App Service Plan + los dos App Services.

A1
Publicar las imágenes Docker en un registro accesible · apps/api · apps/web

Como la app corre en la subscripción del cliente, su App Service tiene que poder descargar las imágenes. Publícalas en un registro público (GHCR o Docker Hub) o en un ACR que la plantilla importe.

bash · desde la raíz del monorepo
# Construir ambas imágenes (versionadas con tag semántico)
docker build -f apps/api/Dockerfile -t ghcr.io/inovabiz/qa-metrics-api:1.0.0 .
docker build -f apps/web/Dockerfile -t ghcr.io/inovabiz/qa-metrics-web:1.0.0 .

# Publicar (el registro debe ser accesible por el cliente)
docker push ghcr.io/inovabiz/qa-metrics-api:1.0.0
docker push ghcr.io/inovabiz/qa-metrics-web:1.0.0

▲ Gap de tu app

Fija tags de versión inmutables (no latest) para que cada versión del offer apunte a una imagen exacta y reproducible.

A2
Blindar el Bicep: secretos generados + Key Vault

Hoy tu main.bicep pasa JWT_SECRET, ENCRYPTION_KEY y DATABASE_URL en texto plano dentro de App Settings. La certificación de Microsoft rechaza secretos en claro: genera los valores dentro de la plantilla y guárdalos en Key Vault.

bicep · deploy/azure/main.bicep
// Genera un secreto si el cliente no lo provee
@secure()
param jwtSecret string = newGuid()
@secure()
param encryptionKey string = newGuid()

resource kv 'Microsoft.KeyVault/vaults@2023-07-01' = {
  name: kvName
  location: location
  properties: { tenantId: subscription().tenantId, sku: { family: 'A', name: 'standard' }, enableRbacAuthorization: true }
}

resource kvJwt 'Microsoft.KeyVault/vaults/secrets@2023-07-01' = {
  parent: kv
  name: 'JWT-SECRET'
  properties: { value: jwtSecret }
}

// En App Settings, referencia el secreto en vez del valor:
// { name: 'JWT_SECRET', value: '@Microsoft.KeyVault(SecretUri=${kvJwt.properties.secretUri})' }
  • Da a cada App Service una identidad administrada y un rol Key Vault Secrets User sobre el vault.
  • Marca todos los parámetros sensibles con @secure().
  • Deriva DATABASE_URL dentro de la plantilla a partir del server + credenciales, no como parámetro plano.
A3
Compilar Bicep → mainTemplate.json (ARM)

El paquete del Solution Template se entrega como ARM JSON. Bicep es solo tu fuente; compílalo al artefacto final.

bash
mkdir -p deploy/azure/marketplace

az bicep build \
  --file deploy/azure/main.bicep \
  --outfile deploy/azure/marketplace/mainTemplate.json

# Valida que el ARM despliega en tu subscripción de pruebas
az deployment group create \
  --resource-group rg-qametrics-test \
  --template-file deploy/azure/marketplace/mainTemplate.json \
  --parameters @deploy/azure/parameters.prod.json

■ Bloqueo si falla

Si el deployment group create no termina limpio en tu propia subscripción, tampoco pasará certificación. Arréglalo aquí antes de seguir.

Prueba el formulario sin publicar nada en el CreateUiDefinition Sandbox: pega el JSON y ve el asistente en vivo.

A5
Empaquetar el .zip del offer

El paquete es un ZIP con los archivos en la raíz (no dentro de una subcarpeta). Mínimo: mainTemplate.json + createUiDefinition.json.

bash
cd deploy/azure/marketplace

# Los archivos deben quedar en la raíz del zip
zip -j qa-metrics-solution-template.zip \
  mainTemplate.json \
  createUiDefinition.json

# (opcional) valida la estructura con arm-ttk antes de subir
# https://github.com/Azure/arm-ttk

■ Error común

Si los .json quedan dentro de una carpeta dentro del zip, Partner Center los rechaza. Usa zip -j (junk paths) o verifica que estén en el nivel superior.

A6
Crear el offer en Partner Center

En Partner Center → Commercial Marketplace → Overview → + New offer → Azure Application.

  • Offer setup: ID interno y alias del offer.
  • Properties: categorías (p.ej. DevOps, Analytics) y sectores.
  • Offer listing: nombre público, descripción, logos (48/90/216px), capturas, video, links de soporte/privacidad.
  • Preview audience: IDs de subscripción autorizadas a ver el borrador.
  • Plans → + Create new plan → tipo Solution template → sube qa-metrics-solution-template.zip.
  • Selecciona las regiones de Azure donde el plan estará disponible.

● Ventaja

El plan Solution template suele publicarse gratis: el cliente paga solo los recursos Azure que despliega. No necesitas configurar el perfil de payout para esta ruta.

A7
Validar, previsualizar y publicar

Al enviar, Microsoft ejecuta certificación automática (valida que la plantilla despliega y cumple políticas).

Checklist antes de Go live

  • La certificación pasa sin errores (revisa el reporte si falla).
  • Instala el offer desde el Preview en una subscripción de prueba, de punta a punta.
  • La app arranca: web responde, API healthcheck OK, Prisma migró contra el Postgres creado.
  • Publicas → Go live → el offer queda listado públicamente.

Ruta B SaaS Offer · facturación por Azure

Vender QA Metrics como SaaS multi-tenant

Tú hospedas una sola instancia; el cliente compra desde el Marketplace y paga en su factura de Azure. Además del empaquetado, esto requiere cambios reales en la app: aislamiento multi-tenant, login federado con Entra ID, y la integración con la Fulfillment API.

B1
Convertir la app en multi-tenant

Hoy cada cliente vive en un deployment con su propia base. Para SaaS, una instancia sirve a muchos tenants con aislamiento de datos. El patrón más simple sobre tu Prisma: columna tenantId en cada modelo + scoping obligatorio.

prisma + express · scoping por tenant
// schema.prisma — añadir a cada modelo de negocio
model Cliente {
  id        String @id @default(cuid())
  tenantId  String            // ← discriminador
  // ...campos existentes
  @@index([tenantId])
}

// middleware express: resuelve el tenant del token y fuerza el filtro
app.use((req, res, next) => {
  req.tenantId = resolveTenantFromJwt(req)   // nunca confiar en el body
  if (!req.tenantId) return res.status(401).end()
  next()
})

▲ Gap de tu app · el más grande

Es la pieza de mayor esfuerzo. Decide entre DB compartida con tenantId (más simple) o schema/DB por tenant (más aislamiento). Toda query debe filtrar por tenant sin excepción.

B2
Registrar la app multi-tenant en Microsoft Entra ID

El Marketplace exige login federado con Entra ID y usa esta app para autenticar los tokens de compra. Regístrala como multi-tenant.

bash · az cli
az ad app create \
  --display-name "QA Metrics SaaS" \
  --sign-in-audience AzureADMultipleOrgs \
  --web-redirect-uris "https://app.qametrics.io/auth/callback"

# Crear un secreto de cliente (guárdalo en Key Vault)
az ad app credential reset --id <appId> --append
  • Anota Application (client) ID y Directory (tenant) ID — van en la configuración técnica del offer.
  • La landing page usará esta app para el SSO del comprador.
B3
Construir la landing page de activación

Tras comprar, Azure redirige al cliente a tu URL con un token de Marketplace en el query string. Esa página inicia el SSO y resuelve la suscripción.

flujo · redirect de Marketplace
# Azure envía al comprador a:
https://app.qametrics.io/?token=<marketplace_token>

# Tu landing (Next.js) debe:
# 1. Autenticar al usuario con Entra ID (SSO)
# 2. Llamar a Resolve con el token (paso B4)
# 3. Mostrar onboarding y activar la suscripción
B4
Integrar la SaaS Fulfillment API v2 — Resolve & Activate

Con el token, resuelves la suscripción y luego la activas. Primero obtén un token de acceso para el recurso del Marketplace.

http · resolve + activate
# 1) Token para el Fulfillment API (client credentials)
POST https://login.microsoftonline.com/<tenantId>/oauth2/v2.0/token
  grant_type=client_credentials
  client_id=<appId>&client_secret=<secret>
  scope=20e940b3-4c77-4b0b-9a53-9e16a1b010a7/.default

# 2) Resolver la suscripción a partir del token de compra
POST https://marketplaceapi.microsoft.com/api/saas/subscriptions/resolve?api-version=2018-08-31
  Authorization: Bearer <aad_token>
  x-ms-marketplace-token: <marketplace_token (url-decoded)>

# 3) Activar (tras elegir el plan en tu onboarding)
POST .../api/saas/subscriptions/<subscriptionId>/activate?api-version=2018-08-31
  { "planId": "pro-monthly" }

■ Importante

El x-ms-marketplace-token viene URL-encoded en el query string. Decodifícalo antes de mandarlo en el header o el Resolve falla.

B5
Implementar el webhook de ciclo de vida

Azure notifica cambios de la suscripción (cambio de plan, cancelación, suspensión, reactivación) a un endpoint tuyo. Debes actuar y confirmar cada operación.

express · POST /api/marketplace/webhook
app.post('/api/marketplace/webhook', async (req, res) => {
  const { action, subscriptionId, operationId } = req.body
  // 1) VERIFICAR: nunca confíes en el body; re-consulta la operación
  const op = await getOperation(subscriptionId, operationId)
  if (op.status !== 'InProgress') return res.sendStatus(200)

  switch (action) {
    case 'Unsubscribe': await deactivateTenant(subscriptionId); break
    case 'ChangePlan':  await applyPlan(subscriptionId, req.body.planId); break
    case 'Suspend':     await suspendTenant(subscriptionId); break
    case 'Reinstate':   await reinstateTenant(subscriptionId); break
  }
  // 2) CONFIRMAR el resultado a Azure
  await patchOperation(subscriptionId, operationId, 'Success')
  res.sendStatus(200)
})
B6
Facturación por uso — opcional

Si además del plan fijo quieres cobrar por consumo (p.ej. nº de HUs analizadas o usuarios activos), emite eventos al Marketplace Metering Service.

http · metering
POST https://marketplaceapi.microsoft.com/api/usageEvent?api-version=2018-08-31
  Authorization: Bearer <aad_token>
  {
    "resourceId": "<subscriptionId>",
    "dimension":  "hus_analizadas",
    "quantity":   1250,
    "effectiveStartTime": "2026-07-08T00:00:00Z"
  }

◆ Tip

Las dimensiones de metering (como hus_analizadas) se declaran primero en el plan dentro de Partner Center; el nombre debe coincidir exacto.

B7
Configuración técnica del offer en Partner Center

En Partner Center → + New offer → Software as a Service → Technical configuration, conecta la app con tu backend:

  • Landing page URL: https://app.qametrics.io (paso B3).
  • Connection webhook: https://app.qametrics.io/api/marketplace/webhook (paso B5).
  • Azure AD tenant ID y Azure AD application ID (paso B2).
B8
Definir planes y precios

En la pestaña Plans crea uno o más planes (p.ej. Starter, Pro) con modelo de precio: tarifa plana mensual/anual, por usuario, o por dimensión de uso. Marca el offer como público o privado.

▲ Requisito · payout

Aquí sí necesitas el perfil de pago y fiscal completo del paso 0.1 para recibir los payouts de Microsoft (comisión del Marketplace aplica).

B9
Probar en Preview y publicar

Checklist end-to-end

  • Con el offer en Preview, ejecuta una compra de prueba desde una subscripción autorizada.
  • El flujo completo funciona: compra → landing → SSO Entra ID → Resolve → Activate → tenant creado.
  • El webhook procesa correctamente ChangePlan y Unsubscribe.
  • (Si aplica) los eventos de metering llegan y se reflejan en la facturación de prueba.
  • Certificación OK → Go live.

FIN Común a ambas rutas

Certificación y publicación

El último tramo es igual para las dos rutas: enviar, pasar la revisión de Microsoft y salir en vivo.

◆
Del envío al Go live
  • Review and publish: Partner Center corre validaciones automáticas + revisión (puede ser manual para SaaS).
  • Preview: el offer queda visible solo para tu audiencia de prueba — valida todo aquí.
  • Go live: promueves el offer y pasa a estar público en el Marketplace (indexación puede tardar horas).
  • Actualizaciones: cada versión nueva (imagen, plantilla, plan) es un nuevo submit que repite certificación.

Recomendación

Empieza por la Ruta A. Ya tienes el Bicep y el pipeline; con blindar los secretos, publicar las imágenes y armar el paquete (mainTemplate.json + createUiDefinition.json) tienes presencia real en el Marketplace en 1–2 semanas — incluso como oferta gratuita o de contacto.

Planifica la Ruta B como evolución. Si el objetivo es vender por suscripción, el bloqueo principal no es el Marketplace sino tu app: multi-tenancy + Entra ID SSO. Aborda eso como un proyecto propio antes de tocar la Fulfillment API.
